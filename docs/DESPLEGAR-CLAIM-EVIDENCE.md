## Ruta recomendada: Supabase Dashboard, sin CLI

1. Abrir el proyecto correcto → Edge Functions → Secrets. Agregar `ALLOWED_APP_ORIGINS` con los orígenes exactos de la aplicación, separados por coma y sin rutas ni barra final. Para Vite local suele ser `http://localhost:5173`; comprobar la dirección real del navegador, porque Vite puede elegir otro puerto. Si se usa también `http://127.0.0.1:5173`, es otro origen y debe añadirse explícitamente. El dominio publicado debe ser HTTPS. No usar `*`. Guardar y confirmar antes de seguir.
2. El archivo único se genera con `npm run prepare:claim-evidence`, sin instalar dependencias. Abrir `.cache/claim-evidence-dashboard.ts`. Contiene exactamente el handler y su validador local, con el SDK npm fijado a 2.118.0; no contiene credenciales. No copiar únicamente el `index.ts` original al editor web: depende de `../_shared/evidence-validation.js`.
3. Supabase → Edge Functions → Deploy a new function → Via Editor. Elegir **`claim-evidence`** como nombre exacto. Sustituir solo el ejemplo inicial de esa función nueva por **todo** `.cache/claim-evidence-dashboard.ts`. No editar otra función existente. Revisar el diagnóstico de tipos del editor Deno y detenerse si muestra errores.
4. Mantener **Verify JWT** habilitado. Las llamadas usan el JWT de sesión en Authorization y la clave pública en apikey. El handler además verifica el usuario con Auth y autoriza cada acción en SQL. No deshabilitar esta comprobación para arreglar un 401 sin analizarlo.
5. Desplegar solo esa función y confirmar el resultado. No introducir claves privadas en el código, en la prueba del editor ni en variables VITE. Supabase proporciona en servidor `SUPABASE_URL`, `SUPABASE_ANON_KEY` y `SUPABASE_SERVICE_ROLE_KEY`. Si falta alguna, diagnosticar su configuración de servidor sin imprimir valores. No hacer público `claim-evidence` ni modificar las políticas de Storage.
6. Avisar cuando aparezca desplegada. Ejecutaremos pruebas A/B/C y una solicitud desde el origen permitido. Una visita GET desde el navegador no prueba una descarga autorizada; sin sesión debe rechazarse. Un OPTIONS con origen permitido debe pasar la preflight. No anunciar éxito por haber desaparecido el 404 solamente.

El archivo generado vive en `.cache`, excluido de Git. Sus fuentes versionables son `supabase/functions/claim-evidence/index.ts`, `supabase/functions/_shared/evidence-validation.js` y el generador. Después de un cambio de esas fuentes hay que regenerar y volver a desplegar. No modificar el generado para divergir de las fuentes revisadas.

El generador añade anotaciones TypeScript al validador JS e incluye dos archivos **solo para VS Code**: `.cache/claim-evidence-editor.d.ts` y `.cache/tsconfig.json`. Resuelven el import `npm:` con los tipos reales del SDK instalado y declaran únicamente la superficie Deno utilizada. La función mantiene `strict: true`; `skipLibCheck` evita revisar las declaraciones internas de dependencias para Node/WebAuthn ajenas a este entorno. No se usa `ts-nocheck`, no se desactiva la validación de TypeScript y no se instalan dependencias. No pegar esos dos archivos de editor en Supabase: allí Deno ya proporciona sus tipos y resuelve `npm:`. Si VS Code conserva avisos anteriores, cerrar y reabrir el archivo o ejecutar `TypeScript: Restart TS Server` desde Ctrl+Shift+P. Los avisos CSS sobre `@tailwind` son independientes de esta función.

Las invocaciones, el almacenamiento y el tráfico consumen las cuotas del proyecto. No se cambia el plan ni se contrata otro servicio; comprobar el plan de Supabase antes de ampliar el uso.

## Cuenta principal de moderación: autorización separada

La cuenta C coincide con el administrador que resolvió el expediente técnico. El propietario ya confirmó la creación de la cuenta D y su inicio de sesión. La comprobación con las credenciales locales confirmó que es distinta de A/B/C, está en `aal1`, no tiene factores TOTP pendientes/verificados y no accede a moderación. Posteriormente, el propietario autorizó expresamente el nombramiento temporal como `reviewer` y su desactivación final, configuró MFA personalmente y ejecutó la consulta individual de nombramiento. Confirmó acceso al panel de D. El agente no configuró factores ni ejecutó SQL administrativo; la desactivación sigue pendiente al terminar las pruebas. Dos cuentas de la misma persona sirven para probar separación de acceso, pero **no acreditan revisión humana independiente en producción**; esa independencia exige otra persona autorizada y sin conflicto de interés.

Antes del nombramiento hay que informar de su alcance real: `reviewer` no está limitado técnicamente al expediente técnico ni tiene vencimiento automático. Con MFA permite leer los expedientes elegibles ajenos, sus pruebas y bitácora, y actuar sobre casos libres o asignados a la propia cuenta; puede solicitar información, registrar resoluciones, revisar apelaciones de otro revisor y aplicar/retirar pausas justificadas de hasta 72 horas. No permite revisar casos donde es comprador/vendedor, la apelación de su propia resolución, sustituir a un revisor ya asignado, nombrar personal, cambiar políticas, editar historial ni mover dinero. Para usar D únicamente en pruebas se requiere autorización explícita de ese acceso temporal y su desactivación posterior, sin presentarlo como aislamiento técnico. Si se exige impedir técnicamente todo acceso a expedientes reales, es necesario preparar y autorizar un control adicional de alcance antes de conceder el rol. Ninguna aprobación general de pruebas sustituye la autorización específica del nombramiento.

1. El propietario identifica su cuenta real por el UUID de Authentication → Users, comprobando personalmente su correo. No usar automáticamente A, B o C, ni enviar contraseñas/códigos MFA por chat.
2. Configurar y verificar el autenticador en Pendejaditas → Mis reclamaciones → Acceso de moderación. El QR TOTP es un secreto personal; no compartirlo. Registrar MFA no concede el rol. Antes del nombramiento la cuenta debe seguir sin acceso administrativo.
   Si quedó un intento sin terminar, la interfaz consulta `listFactors().all` (el SDK solo incluye verificados en `.totp`). Se puede introducir el código del intento pendiente ya escaneado. Si se perdió el QR, el botón «Perdí el QR: reiniciar configuración pendiente» solicita confirmación y vuelve a comprobar que sea un TOTP no verificado creado por Pendejaditas; solo entonces descarta ese intento y genera otro. Nunca elimina factores verificados ni concede roles. Los QR se limitan a 256 px, conservan proporción y margen blanco; se incluye clave manual privada y enlace al autenticador para dispositivos compatibles. No se guardan esos secretos en localStorage. Si el servidor confirma `aal2` pero falta el rol, se explica que el nombramiento administrativo sigue pendiente.
3. Confirmar explícitamente el UUID y el rol antes de cualquier nombramiento. `reviewer` basta para revisar casos ajenos, pruebas, solicitar información, resolver y revisar apelaciones de otro revisor. `supervisor` añade capacidad de actuar en casos asignados a otro revisor; usarlo solo si la cuenta principal necesita esa coordinación. Ninguno concede acceso SQL, gestión de claves, pagos o permiso para nombrar más personal desde el navegador.
4. Solo después de esa autorización, el propietario ejecuta **una llamada a `set_moderation_staff`** desde SQL Editor, con UUID comprobado, rol elegido, `true` y justificación. No repetir la migración, editar tablas a mano, conceder `service_role` ni modificar JWT/metadatos de usuario para simular un administrador. La función registra el nombramiento. No se incluye una instrucción rellenada hasta que el propietario confirme la identidad y alcance.
5. Iniciar sesión con segundo factor. Probar que sin `aal2` no haya acceso; con MFA sí, pero siempre excluyendo comprador y vendedor del expediente. Un supervisor también tiene prohibido revisar/resolver su propio caso. El autor de una resolución no revisa su apelación; se necesita otra cuenta real autorizada con MFA para probar ese flujo completo.
6. Probar resoluciones concurrentes, solicitudes de información, auditoría, pausas con vencimiento y retiro justificado. Las pruebas no deben usar casos comerciales ni otorgar roles automáticamente a las cuentas de pruebas. La bitácora preserva acciones originales; un dueño de base de datos sigue siendo una autoridad de confianza capaz de cambiar el sistema, no una garantía de inmutabilidad externa.

No hay pagos, reembolsos, liberación de dinero, protección física garantizada ni decisiones automáticas de culpabilidad. No publicar en GitHub hasta terminar la integración y las pruebas autorizadas.
